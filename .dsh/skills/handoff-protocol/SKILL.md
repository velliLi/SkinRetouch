# 多对话交接规范

本项目按对话并行推进（算法、Web 服务、文档各自一条线），对话之间**不共享上下文**，唯一可靠的传递介质是工作区文件加 git 历史。交接文档写不好，下一个对话就要把踩过的坑重新踩一遍。`git` 的操作细节见 `git-workflow` skill，本文只管**交接内容怎么组织**。

## 一、接手时先做的三分钟检查

```powershell
git -C E:\SkinRetouch log --oneline -5
git -C E:\SkinRetouch status -sb
git -C E:\SkinRetouch diff --stat
```

读完 `HANDOFF.md` 再跑这三条，判读规则：

- `status` 出现 ` M`（已跟踪文件被改）或 `??`（未追踪新文件），说明**另一个对话正在开发，这些改动属于它**。
- 此时**绝不** `git add -A`、`git add .`、`git commit -a`——那会把别人写了一半的东西打包提交。
- 只按确切路径暂存自己的文件：`git add .dsh/skills/handoff-protocol/SKILL.md`。
- 提交前用 `git status --porcelain` 复核一遍暂存清单，确认里面没有不属于本次任务的条目。

这条是实测教训：曾出现工作区有 4 个 ` M` 和 4 项 `??`（`run_server.py`、`server/`、`tests/server_test.py`、`tests/_probe_gray.py`）由另一条对话产出的情况，`add -A` 会直接把它们卷进来。

## 二、唯一交接介质

`E:\SkinRetouch\HANDOFF.md`，一份，随代码一起提交。

不按对话拆分文档，不写进 issue 或 wiki。分叉出 `HANDOFF-算法.md` / `HANDOFF-服务.md` 会立刻失去同步——两份都在描述同一个 `skin_retouch()`，读者无法判断哪份是新的。新模块（如 `server/`）的做法是在**同一份文档里加章节**，不是另开文件。

## 三、HANDOFF.md 各节写什么

现有文档按**主题**组织，不按时间堆积。新内容并入对应主题章节，不新增"第 N 轮开发记录"。

| 章节 | 必写 | 禁写 |
|---|---|---|
| 这是什么 | 一句话定位、输入输出、当前状态（可用/实验/废弃） | 营销话术、"强大的" |
| 三十秒跑通 | 可直接粘贴的命令 + 期望出现的关键字（`DONE`、`NODE OK`、`SERVER OK 47 checks`） | 需要读者自己拼的命令片段 |
| 环境事实 | 解释器绝对路径、显卡与显存、库版本、模型体积与归属 | "装好依赖即可" |
| 不要推翻的决定 | 每条 = 决策 + 理由 + 支撑数据 | 无理由的结论 |
| 算法怎么走 | 为什么这么走、哪一项在起作用 | 代码复述 |
| 旋钮 | 参数表、默认值、双默认值陷阱 | 只说参数名不说后果 |
| 实测数据 | 每个数字带环境（CPU/GPU、图幅、人脸 px、冷热态） | 孤立的"变快了" |
| 已知限制 | 缺陷 + 为什么可以接受 | 回避缺陷 |
| 可以继续的方向 | 可执行起点 + 判据 | 愿望清单 |
| 文件 | 目录树 + 每项一句职责 | 只列名字 |

**「不要推翻的决定」是全文档最重要的一节。** 没有理由的决策，下一个对话一定会推翻它——因为它看起来只是随手写的常量。对照现有条目：不用扩散模型重绘（理由：身份漂移）、不用 mediapipe（理由：protobuf 冲突实测崩溃 + 降级代价）、检测不上卡（理由：CPU 与 CUDA 实测同为 0.19 s，瓶颈是 `cv2.resize`）、不做 Tkinter 窗口（理由：出这台机器即废）、单 worker 串行（理由：6 GB 显存 + ComfyUI 常驻必然 OOM）。每条都能被验证，所以没人会去动它。

模块自带决策时，在该模块章节下再开一个「不要推翻的决定」子节即可（`server/` 就是这么做的），但要保证两条同名子节各自的作用域在标题下第一句就写明，否则读者不知道限制的是全局还是局部。

## 四、必须留证据的四类内容

丢掉这些，下一个人就会重做已经失败的尝试：

1. **失败路线的取证物**。`tests/probe_*.py` 里 15 个（cluster/sam/gate/skin/regions 系列）是废弃路线的现场，不参与验收但必须保留，文件树里要标注它们的用途。
2. **数值基线**。三行 `hf-energy` 是回归判据，任何改动后数值变了必须在交接里解释变了什么、为什么。
3. **踩坑的复现条件**。写成别人能复现的形式，而不是"这里有个坑"：
   - 7861 端口落在 `netsh int ipv4 show excludedportrange protocol=tcp` 的 7779–7878 保留段，绑定报 `WinError 10013`，所以默认端口是 8791。
   - 拒绝请求前不读掉 body，客户端收到 RST 看到 `ConnectionAbortedError` 而不是 401，表现为网络错误、不弹令牌框；`api.py:_drain_body()` 先吃 body 再回错。
   - CSS `line-height: 0` 让子标签行盒塌成 0 高，字形被切一半，表现为一排彩色碎片。
4. **不可分的已知缺陷**。浅粉/肉色紧身衣（`Cr147 Cb123`）与皮肤色度完全相同，纹理判据也救不了，`DSC_7300` 左腰那片就是——接受它的理由是该布料本身平滑，美肤对它的实际改动接近零。

反例对照：写"身体掩膜效果一般"零信息；写"色度椭圆参考色必须锚定人脸，在 person 掩膜内迭代估会收敛到全图中位数 `[140,134,128]`，整件衣服被选中占 person 面积 80%"，下一个对话才能避开。

## 五、并行开发时的写区划分

同一条对话只碰自己那一列，跨界前先在交接里说明：

| 对话线 | 写区 | 不碰 |
|---|---|---|
| 算法 | `skin_core.py`、`skin_body.py`、`skin_gpu.py`、`tests/blemish_test.py`、`tests/compare_paths.py` | `server/`、`run_server.py` |
| Web 服务 | `run_server.py`、`server/`、`tests/server_test.py` | 三个算法模块 |
| 文档与规范 | `README.md`、`HANDOFF.md`、`OPTIMIZATION_AUDIT.md`、`.dsh/skills/` | 同上 |

`skin_retouch_node.py` 与 `__init__.py` 是交汇点，改动前先跑一次 `git status` 确认没有未提交的同名改动。

**HANDOFF.md 是唯一的共享写区**，冲突概率最高。规则：只 append 到自己负责的章节，不要整段重写别人刚加的子节；发现自己要改的位置有未提交改动，先提交自己的部分或等对方提交，不要覆盖对方未保存的编辑。

## 六、结束一轮开发时

交接块写进对应主题章节，格式固定四段，缺一段就等于没交接：

```markdown
### <主题>

**做了什么**：一句话说清结果，带关键数字。
**为什么这么定**：被否决的替代方案及其失败原因。
**没做什么**：明确划出边界，避免下一个对话以为漏了。
**怎么验证**：可粘贴的命令 + 期望输出关键字。
```

不要写日期流水账（"今天又优化了一次"），git 已经记了时间；不要复述代码（`git show` 能给）；不要留没有判据的 `TODO`。

## 七、文档与代码的一致性

- **描述资产去向的句子必须同时给出仓库视角。** 现有反例：`HANDOFF.md` 的「环境事实」写模型"随项目自带"，那是本机视角，仓库视角是 `.gitignore` 排除了 `models/*.pt`，新 clone 后必须手动补齐。这类句子要写成"本机已有 / 仓库不含 / 补齐方式"三段。
- **声称可用的功能必须附可执行验证命令。** 说服务能用，就得有 `tests/server_test.py` 的 `SERVER OK 47 checks`。
- **改行为的那次提交同时改文档**，不要留到"下次整理文档"——那一步永远不会来。
- 运行时产物一律忽略：`server/data/`（上传原图、成图、掩膜、`meta.json`）、`.shot/`、`tests/output/`、`tests/assets/`、`.yolo/`。

## 八、反模式

- 时间流水账代替主题组织。
- 复述代码实现，不写决策理由。
- 没有环境与量纲的性能数字。
- 无判据的 `TODO`、`FIXME`、"后续优化"。
- 把交接内容写进 commit message 就以为交接完了（commit 面向审查，HANDOFF 面向接手）。
- 覆盖另一个对话未提交的编辑。
- 另开一份交接文档。
